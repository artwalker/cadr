# Proposal: Goal 20 — liveness assertions for agent-turn output (queue item 12E-1)

Status: **awaiting adjudication**. Requested by the advisor ruling of
2026-08-15 (goal20-state.md item 12E-1: "立项,但报告低估了工作量,先出提案").
This file answers the four required questions in §§1–4. §5 is the pilot
measurement that §3 depends on. No gate, ledger, or capture format is
changed by this file.

## Why

All five real-terminal escapes in goal 20 (latest: P0-4, "cadr shows
nothing during an agent turn while pi shows progress throughout") sit in
the **time dimension**. Every current assertion is a static checkpoint —
a safety property ("nothing wrong is shown"). None can express a liveness
property ("something is eventually shown"): a perfectly silent
implementation passes all of them (Alpern & Schneider, *Defining
Liveness*, 1985; report §03.6). The checkpoint oracle is structurally
blind here, and five escapes have landed in that blind spot.

## 1. Capture format change

Additive sidecar only. For each existing `{scenario}.{dimension}.{side}.raw`
the capture writes one `{...}.timing.json`: an array of
`[t_seconds, chunk_bytes]`, one entry per PTY read.

- Recording point: the only two `os.read` call sites,
  `read_ready` (`scripts/render-diff.py:2057-2070`) and `drain`
  (`:2073-2086`). No other byte path exists.
- Entries are keyed to the capture's PTY master fd, tracked across
  `os.openpty`/`os.close`. **The pilot proved this matters**: tracking
  only `openpty` polluted the cadr log with 5.8MB of unrelated file reads
  after fd reuse; fd lifecycle tracking produced logs whose byte sums
  match the `.raw` length exactly (32,107 and 20,329 bytes).
- The `.raw` format is **untouched** and stays byte-identical. Old
  artifacts remain fully valid; no historical evidence is invalidated.
  The sidecar is derived data — it can be regenerated by re-capture and
  is never an input to existing classification.
- Byte offset → time mapping is exact: checkpoint offsets are byte counts
  into `.raw`, and the sidecar's cumulative `chunk_bytes` reproduce those
  offsets (validated in the pilot, §5).

## 2. Baseline re-capture: scope and cost

- Scope: the **33 agent-turn scenarios** (the scenarios.json entries whose
  actions drive a model turn; the remaining 37 startup/cli/commands
  scenarios have no turn window and get no liveness assertion).
- pi side: 33 scenarios × 2 dimensions = **66 re-captures** at the pinned
  baseline. The baseline cache `/tmp/cadr-render-diff-pi-53fa77ccd`
  exists and is current (marker matches `BASELINE`); node v22 is
  available. Measured pilot cost: 8 captures (4 scenarios × 2 sides)
  completed in under 10 minutes including process boot ⇒ the 66-capture
  pi re-measurement is a **one-off ~30–45 minute** scripted run.
- cadr side: captured at implementation time, same manifest.
- Non-agent scenarios keep their existing artifacts untouched.

## 3. How N is set

Data first, threshold second (per the ruling; development-policy §5.5
forbids setting the criterion before the measurement).

Pilot distribution, pi side, agent-turn scenarios, wide dimension,
2026-08-15 (method in §5; n = PTY reads during the capture):

| Scenario | n | median gap | p95 gap | worst gap |
|---|---:|---:|---:|---:|
| conversation-content | 78 | 0.5 ms | 39.7 ms | **102.1 ms** |
| tools-success | 305 | 0.5 ms | 21.2 ms | 69.6 ms |
| stream-interrupt-queue | 258 | 79.4 ms | 81.0 ms | 82.2 ms |
| conversation-mermaid | 70 | 0.5 ms | 21.5 ms | 50.7 ms |
| **pi aggregate** | **711** | — | — | **102.1 ms** |

cadr side in the same pilot is healthy (worst 106.1 ms), confirming the
assertion's initial value is a **regression lock**, not a bug fix.

Proposed rule: per-scenario `N_i = max(10 × pi_worst_i, 500 ms)`, computed
from the full 66-capture re-measurement (§2), published as a table in the
implementation's acceptance report. With pilot data this yields N ≈ 1.0 s
for unpaced scenarios. Rationale for the 10×/500 ms floor: the measured
worst is 102 ms, machine-load variance on shared hosts is real, and a
threshold set near the noise floor manufactures false reds — the I04
corrosion path.

Two definition notes:

- **Assertion window**: from the first output byte to the last output byte
  of the capture. Boot silence before the first byte and teardown after
  the last are excluded by construction — mid-turn silence (the P0-4
  shape) is interior and covered.
- **Paced scenarios** (e.g. stream-interrupt-queue at ~80 ms pacing)
  establish their own floor; per-scenario N_i absorbs this. A global
  constant would either false-red the paced scenarios or go permissive
  everywhere else.

## 4. Deterministic or statistical

**Statistical.** Wall-clock timing on a loaded host is not deterministic;
the ruling's lean is correct. Concretely:

- New stage, separate from the deterministic tier: n = 3 captures per
  scenario, criterion "worst inter-output gap ≤ N_i in every run".
- Failure output includes the full gap distribution, not just red — the
  diagnostic value is in the tail.
- Lives outside `render-diff.py gate --tier core`; wired into
  `scripts/verify.sh` as its own stage so the deterministic gate's cost
  and false-red profile are unchanged.

## 5. Pilot appendix (method and reproduction)

Throwaway pilot, 2026-08-15, cadr HEAD `22551cd0a`, baseline cache
`53fa77ccd`, wide dimension:

- `/tmp/liveness-pilot/pilot.py` loads `scripts/render-diff.py` as a
  module (it is main-guarded, `render-diff.py:3925`), patches `os.read` /
  `os.openpty` / `os.close` to log `[monotonic, fd, bytes]`, and invokes
  the stock `capture()` (`render-diff.py:3022`) per side. No repository
  file was modified; artifacts under `/tmp/liveness-pilot/out`.
- Validation: per-side logged byte sums equal the `.raw` lengths exactly
  (pi 32,107; cadr 20,329), so the offset mapping is lossless.
- cadr numbers for contrast: conversation-content max 106.1 ms (median
  19.9 ms), tools-success max 85.1 ms, stream-interrupt-queue max 87.6 ms,
  conversation-mermaid max 86.3 ms.

Known coverage limit, stated honestly: current scenarios stream promptly,
so the pilot exercises rendering rhythm, not first-token latency. P0-4's
real-world silence was seconds long and is not reproduced by any existing
scenario. Closing that needs a **silence-injection scenario**: a turn
whose faux stream delays its first token (achievable today with a very
low `tokensPerSecond`; a cleaner `initialDelayMs` knob in both faux
drivers would be test-only code). That scenario is a follow-up item, not
part of this proposal's enablement.

## Enablement (ordered)

1. Timing sidecar + offset mapping + self-test coverage (no assertion
   yet; deterministic, additive).
2. Full 66-capture pi re-measurement; publish the per-scenario
   distribution table in the acceptance report.
3. Per-scenario N_i adjudicated from that table (§3 rule).
4. Statistical liveness stage in `scripts/verify.sh` (§4 shape).
5. Follow-up, separately proposed: silence-injection scenario for
   first-token latency (the actual P0-4 shape).
